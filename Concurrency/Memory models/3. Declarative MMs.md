## The Abstraction : Declarative MMs

Мы установили, что разные аппаратные архитектуры предоставляют определённые гарантии на уровне инструкций. Однако писать переносимый, человекочитаемый и корректный параллельный код, полагаясь исключительно на низкоуровневые барьеры памяти и знание конкретной архитектуры - это слишком непосильная и насыщенная ошибками задача.

Эта модель служит двум целям. Во-первых, она даёт нам абстрактный, платформо-независимый набор правил для рассуждения о поведении программы. Во-вторых, она служит спецификацией для разработчиков компиляторов, указывая им как транслировать высокоуровневые инструкции языка, связанные с обращением к памяти, в машинные инструкции.

---
### Sequential Consistency

Для построения работующего контракта, необходимо иметь точку отсчёта - некоторый идеал, к которому мы будем устремлять поведение наших программ. В мире моделей памяти таким идеалом является **Последовательная согласованность (`Sequential Consistency, SC`)**.

Формальное определение `SC`, данное Лэсли Лэмпордом, звучит следующим образом :

`...результат любого исполнения тот же самый, как если бы операции всех процессоров/потоков выполнялись в некотором последовательном порядке, а операции каждого отдельного процессора/потока появлялись бы в этой последовательности в порядке, определённом этой программой. (Lamport, 1979, How to make a Multiprocesor Computer that correctly executes Multiprocess programs).`

Проще говоря, модель `SC` представляет исполнение программы как простое перемешивание инструкций (`interleaving`) из разных потоков, при котором сохраняется их исходный `program order` внутри каждого потока. Эта модель очень интуитивна и является золотым стандартом предсказуемости поведения.

#### The High Cost of Pure Sequential Consistency

Если `SC` так проста, то почему бы просто не потребовать от всех языков и процессоров её реализации? Ответ конечно же кроется в производительности.

Требование строгой `SC` для каждой операции с памятью по сути запрещает почти все аппаратные и компиляторные оптимизации, которые мы обсуждали ранее :

- `SC` запрещает ядру использовать `store buffer`, т.к. любая запись должна становиться глобально видимой до выполнения следующей инструкции.

- `SC` запрещает очередь инвалидации, т.к. инвалидация должна происходить немедленно.

- `SC` запрещает компилятору переупорядочивать независимые обращения к памяти (например `X = 1`, `r1 = Y`), т.к. это нарушает программный порядок в глобальном `interleaving`.

Строгая реализация `SC` также означала бы, что после каждого обращения к памяти, процессор должен был бы устанавливать полный барьер, что свело бы на нет все преимущества многоядерности. Системы, предоставляющие такую гарантию, были бы неконкурентоспособно медленными.

Думаю уже становится понятно, к чему я веду. Видно, что в этой ситуации необходим компромисс, который позволил бы сохранить простоту и предсказуемость `SC` для корректных программ, но при этом дал бы свободу компилятору и аппаратуре применять оптимизации там, где это безопасно. На этом компромиссе и основаны современные декларативные модели памяти.

### `DRF-SC` (Data-Race-Free implies SC Guarantee)

Компромисс, который был найден и лёг в основу моделей памяти `Java, C++, Swift`, известнен под названием `DRF-SC`. Это центральная идея всех современных декларативных моделей памяти. Фактически, является главным пунктном протокола между программистом и системой (компилятор + процессор).

Формулируется контракт следующим образом :

`Если программа написана так, что в ней отсутствуют гонки данных, то система гарантирует, что любое её исполнение будет эквивалентно некоторому последовательно согласованному исполнению (Sequential Consistency). Если же в программе есть гонка, её поведение не определено (UB). (Boegm & Adve, "Foundations of the C++ Concurrency Memory Model").`

Важнейшее следствие этого контракта - если в нашей программе нет гонок, нам не нужно думать о аппаратных оптимизациях или специфике архитектур. Мы можем рассуждать о своей программе так, словно все инструкции просто перемешиваются в едином временном потоке. Система берёт на себя всю грязную работу по расстановке необходимых барьеров и запрету небезопасных оптимизаций, чтобы поддерживать иллюзию строгого `SC` для нас.

Однако, если программа содержит гонку, этот контракт аннулируется. Система снимает с себя все обязательства. 

Этот подход позволяет системе применять агрессивные оптимизации по умолчанию, исходя из предположения, что код написан без гонок. Обязанность доказать это системе, расставив атомарные маркеры, ложится на нас.

#### Defining a Data Race

Модель `DRF-SC` будет не более чем размахиваниями руками, если строго не сформулировать понятие `Data Race`. Это определение состоит из двух частей.

Сначала введём понятие конфликта : 

`///! Два обращения к памяти конфликтуют, если они обращаются к одной и той же ячейке памяти, и по крайней мере одно из этих обращений - запись.`

( => два чтения из одной ячейки не конфликтуют, а вот чтение и запись - конфликтуют. Две записи также конфликтуют).

Имея это определение, мы наконец можем сформулировать что такое `Data Race` :

`///! Гонка Данных (Data Race) - это два конфликтующих неатомарных обращения к памяти из разных потоков, которые не упорядочены между собой отношением H-B.

Здесь упоминается ` не упорядочены через H-B`. В формальной модели это означает, что между двумя обращениями нет отношения `happens-before`, которое мы формально введём чуть позже.

=> Задачей программиста, стремящегося к `DRF-SC` является расстановка достаточного количества синхронизирующих операций для установления отношения `happens-before` между всеми потенциально конфликтующими обращениями.

### Events and Partial orders

Теперь настало самое время перейти к формальному аппарату, описывающему гарантию `SC-DRF`.


Как упоминалось ранее, декларативная модель памяти описывает исполнение через набор формальных математических правил, которым должно подчиняться любое допустимое исполнение программы (в которой происходит обращение к памяти). 

В основе модели лежит множество формальных понятий, начнём с самых примитивных :

***`///!` Событие (`Event / Action`)*** - это минимальная единица исполнения, представленная операцией обращения к памяти. Каждое такое событие в абстрактном исполнении - это узел в графе исполнения.

***`///!` Частичный порядок*** - это отношение между элементами множества (в нашем случае между событиями), которое является транзитивным, антисимметричным и иррефлексивным. НО : оно вообще не обязано существовать для любой пары событий.

Разберёмся с указанными ограничениями на наше отношение и как они описывают причинность:

- *Иррефлексивность* : (`A not -> A`) задаёт ограничение, что событие не может предшествовать самому себе.
 
- *Антисимметричность* : (`if A -> B => B not -> A`) задаёт направление порядка.

- *Транзитивность* : (`if A -> B && B -> C, => A -> C`) является фундаментом синхронизации. Если поток `T1` совершил события события `A -> B`, `B -> C` а после этого поток `T2` совершил иные 2 события `C -> D`, то свойство транзитивности позволяет утверждать, что событие `A` произошло до события `D`.


	
***Если между двумя событиями нет отношения порядка, они считаются неупорядоченными, а в нашей модели называются конкурентными (`concurrent`).*** 

Вообще говоря, конкурентные события не обязаны происходить в один момент времени. Для нас скорее важно, что для таких событий модель памяти не даёт нам *никаких гарантий* относительно порядка их исполнения.

---

Теперь рассмотрим конкретные отношения (рёбра), которые соединяют узлы (события) в графе исполнения.

---
#### Sequenced-Before (Program Order)

`///!` `Sequenced-Before (sb)` - это самое базовое отношение, устанавливающее тотальный программный порядок событий в пределах одного потока. 

Если в исходном коде в рамках одного потока операция `A` предшествует операции `B`, то `A` является `sequenced-before` `B`. 

То есть это отношение создаёт локальную временную шкалу событий для каждого отдельного потока. Благодаря ему мы можем формализовать программный порядок инструкций.

---
#### Synchronizes-With

С помощью `sb` мы можем связывать операции внутри одного потока. Но как установить причинно-следственную связь событий между разными потоками? 

`///!` `Synchronizes-With (sw)` - это отношение порядка между событиями в разных потоках. Оно возникает между парой атомарных операций над одной и той же переменной. Если говорить неформально, то между двумя событиями устанавливается 'канал связи', который позволяет упорядочивать операции между потоками.

---
#### Happens-before

Имея локальный порядок в потоках (`sb`) и мосты между ними (`sw`), мы можем построить глобальное отношение причинности - `happens-before.

`///! `Happens-Before (`hb`)` - это отношение, являющееся транзитивным зымыканием объединения отношений `sb` и `sw`.

Операция `A h-b B`, если `A s-b B`, или `A s-w B`, или существует такая операция `C`, что `A h-b C` и `C h-b B`.

![600](https://i.imgur.com/HetuSs5.png)


Это самое важное отношение в модели. Его основная гарантия такова : если `A h-b B`, то все побочные эффекты, произведённые операцией `A` и всеми операциями, которые `h-b A`, гарантированно видны операции `B`. На графе исполнения `hb` - это существование любого пути от `A` к `B`, состоящего из рёбер `sb` и `sw`.

---
#### Modification Order

Для каждой атомарной переменной, модель определяет `modification order (mo)` - строгий тотальный порядок всех её атомарных модификаций.

Этот порядок является единым для всех потоков и концептуально представляется так, что если бы все записи в атомарную переменную `x` выстраивались в одну логическую очередь, где каждая следующая модификация заменяет результат предыдущей.

---
#### Synchronization Order

Даже имея локальный порядок `sb` и возможности устанавливать связи через `sw`, мы всё равно можем смоделировать и получить в результате поведение `r1 == r2 == 0`.

Поэтому мы вводим новую, более сильную гарантию, которая бы позволяла избавиться от подобного поведения. Нам нужен глобальный сквозной порядок на обращениях ко всем атомикам. Назовём его порядком синхронизации или `synchronization order (so)`.

`///! Synchronization order` - это строгий тотальный порядок, определённый на множестве всех обращений ко всем атомарным объектам в программе.

Мы не хотим упорядочивать все обращения к памяти из соображений производительности. Поэтому наши требования мы будем накладывать только на некоторое подможество объектов (атомики). Мы потребуем, чтобы они выстраивались в единую глобальную очередь, с которой согласны все потоки. Разумеется, этот порядок должен быть согласован с `sb / program order` : если в потоке операция `A` стоит раньше `B`, то и в глобальном `so` `A` должна находится раньше `B`.

---

Получив `so`, мы фактически смоделировали `seq_cst`. Формально мы можем выразить его как комбинацию двух гарантий : 

- `seq_cst = SO + HB`

![500](https://i.imgur.com/kLXQzaa.png)

В этой композиции каждый компонент отвечает за свой слой гарантий согласованности.

Порядок синхронизации (`so`) работает исключительно на уровне атомиков. 

В свою очередь, отношение `hb` отвечает за видимость всех остальных неатомарных обращений. Механизм следующий : когда согласно порядку `so` атомарное чтение в одном потоке наблюдает результат атомарной записи другого потока, между ними устанавливается связь `sw`. Объединяясь с внутрипоточным порядком `sb`, эта связь замыкает транзитивную цепь `hb`. Именно это гарантирует, что любые побочные эффекты (например инициализация полей структуры или запись в буфер), выполненные до атомарной записи (согласно `sb`), будут гарантированно видимы и корректно прочитаны после соответствующего атомарного чтения.


Разберем вторую часть подробнее : представим сценарий, где один поток подготавливает данные, а затем сигнализирует об этом через атомарный флаг.

``` C++
// Message passing

int Payload = 0;
std::atomic<int> Guard = 0;

// Thread#1 (Producer)
Payload = 61; // Event A (write payload)
Guard.store(1, std::memory_order_seq_cst); // Event B (write atomic)

// Thread#2 (Consumer)
while (Guard.load(std::memory_order_seq_cst) != 1); // Event C
int r1 = Payload; // Event D (read payload)
```

В этом примере инициализация `Payload = 61` является тем самым побочным эффектом, который выполняется до атомарной записи флага (`event B`) согласно локальному порядку `sb`. 

Когда поток потребитель успешно считывает флаг (`C`) между записью и чтением возникает `sw`. И благодаря транзитивности `hb`, эта связь объединяет два локальных порядка `A -> B` и `C -> D` в цепь 
`A -> B -> C -> D`, что гарантирует : к моменту чтения данных в событии `D`, все эффекты события А уже произошли и полностью видимы, исключая возможность прочитать устаревшее значение `0`.
